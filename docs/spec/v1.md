# v1 Implementation Spec

An Android CalDAV/CardDAV sync provider with per-Account custom HTTP headers and client-certificate authentication.

**Write-back v1**: the server is the source of truth. An edit made on the phone reaches the server when the user has made that Collection writable, and a server-side change made in the meantime wins ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)).

Every decision below links to the ticket that made it. Vocabulary is defined in [`CONTEXT.md`](../../CONTEXT.md) — *Account*, *Collection*, *Credentials*, *Origin* are used in its precise senses throughout.

---

## 1. Scope

### In

- Per-Account custom HTTP headers, sent on every request
- Client certificate from the Android KeyChain, with or without password auth
- Basic auth alongside either
- Manual configuration, with optional discovery from a user-supplied root
- Contacts (`ContactsContract`) and events (`CalendarContract`)
- Write-back: an edit made on the phone is uploaded to the server for a Collection the user has made writable, and a Collection that is left read-only refuses the edit and says why (§6 step U, §7)
- Honest error surfacing: HTTP status, first line of the response body, whether a certificate was offered

### Out

Tasks (VTODO) · web UI or server component · CalDAV scheduling, free-busy, sharing, ACL · merging a conflict, which is resolved by the server's version winning ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)) · forking an existing DAV client.

**Read-only per Collection** is back, as a per-Collection switch that defaults off ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)). [#14](https://github.com/t1nk333r/dav-provider-android/issues/14) dropped it as meaningless while v1 was read-only everywhere; it is meaningful again now that an edit can be pushed.

`dav4jvm` is JitPack-only, so `settings.gradle.kts` needs the repository **scoped to that group** — an unscoped entry would let any dependency resolve from JitPack:

```kotlin
maven("https://jitpack.io") { content { includeGroup("com.github.bitfireAT") } }
```

**Do not use `ical4android`.** It is GPL-3.0 and archived, superseded by `synctools`, itself archived and folded into DAVx⁵. Design reference only, never a dependency.

**dav4jvm supplies no sync algorithm.** No ETag/CTag comparison, no sync-token handling, no batching, no sync loop. Section 6 is therefore this project's own code, not library configuration.

**Known upstream defect to design around** — [dav4jvm#209](https://github.com/bitfireAT/dav4jvm/issues/209), open: `DavResource.location` is mutated in place by redirect handling while `propfind`/`multiget`/`calendarQuery` flows are lazy, so building several flows from one `DavResource` before collecting can make an earlier flow use a redirected URL. Mitigation, which §6's loop must follow: **one `DavResource` per Collection, collect immediately, and persist `getLocation()` yourself.**

If overriding KGP proves unacceptable, the documented fallback is **dav4jvm 3.0.2**, which Kotlin 2.2.x compiles — at the cost of 4.0.0's suspend/Flow API and 4.0.1's preemptive-Digest auth fix.

## 3. Manifest and resources

`AndroidManifest.xml`:

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.READ_SYNC_SETTINGS" />
<uses-permission android:name="android.permission.WRITE_SYNC_SETTINGS" />
<uses-permission android:name="android.permission.READ_SYNC_STATS" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
<uses-permission android:name="android.permission.READ_CONTACTS" />
<uses-permission android:name="android.permission.WRITE_CONTACTS" />
<uses-permission android:name="android.permission.READ_CALENDAR" />
<uses-permission android:name="android.permission.WRITE_CALENDAR" />
```

`RECEIVE_BOOT_COMPLETED` is **required**, not optional: without it JobScheduler rejects the persisted job the sync framework creates.

`res/xml/authenticator.xml`:

```xml
<account-authenticator xmlns:android="http://schemas.android.com/apk/res/android"
    android:accountType="app.davkeep"
    android:icon="@mipmap/ic_launcher"
    android:smallIcon="@mipmap/ic_launcher"
    android:label="@string/account_type_label" />
```

`res/xml/syncadapter_contacts.xml` (and `syncadapter_calendar.xml` with `contentAuthority="com.android.calendar"`):

```xml
<sync-adapter xmlns:android="http://schemas.android.com/apk/res/android"
    android:contentAuthority="com.android.contacts"
    android:accountType="app.davkeep"
    android:userVisible="true"
    android:supportsUploading="true"
    android:allowParallelSyncs="false"
    android:isAlwaysSyncable="true"
    android:settingsActivity="app.davkeep.ui.SettingsActivity" />
```

- `supportsUploading="true"` is what the **framework** reads ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)): when a provider reports a dirtying write it asks for an upload-only sync, and such a run uploads and does not list (§6). It is not what a stock editor consults, so flipping it changes what is requested, not what is offered.
- `<EditSchema>` in `res/xml/contacts.xml` is the editor's gate, and this is the one the Contacts app obeys: `ExternalAccountType.areContactsWritable()` returns `mHasEditSchema`, a flag set only by meeting that tag, so without it the account is absent from "Save contact to" however the flag above is set. Declaring it also makes four data kinds mandatory rather than supplied by a fallback — the `name` kind gives `StructuredName` and the pseudo name and phonetic-name kinds, and `Photo` is the fourth — and `checkKindExists` throws on the first one missing, leaving the account type **invalid rather than read-only**. Every kind the editor may write must therefore be named, and the verbatim vCard kind stays declared outside the schema, where no field is rendered for it.
- The Calendar app needs neither: it offers a **writable** calendar from its `CALENDAR_ACCESS_LEVEL`, which the mapper writes per Collection (§7).
- `userVisible="true"` is what creates the per-authority sync switches.
- `isAlwaysSyncable="true"` initialises `isSyncable` to 1 per new Account.
- `settingsActivity` **must** be in the same package.

There is **no** `calendar.xml` platform resource — only Contacts has provider metadata, in `res/xml/contacts.xml`. It is optional for syncing and required for the account to be editable.

## 4. The Account ([#10](https://github.com/t1nk333r/dav-provider-android/issues/10))

One Account per server, spanning many Collections. One Account **is** one `AccountManager` account.

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `label` | string | yes | User-visible; defaults to hostname; **the identity key** |
| `baseUrl` | URL | yes | Editing triggers wipe-and-refetch behind a confirmation |
| `headers` | list of (name, value) | no | Values are secrets: masked, Keystore-wrapped |
| `certAlias` | string | no | KeyChain alias only; the key is never held |
| `username` | string | no | Legal without a password |
| `password` | string | no | Keystore-wrapped |
| `collections` | list of selections | no | From discovery (§8) |
| `formatVersion` | int | export only | Unknown versions are refused, never guessed |

**Legality**: `baseUrl` required; everything else optional, including all-empty. No form rule demands a credential — an unauthenticated LAN server is legitimate, and the two-layer case (proxy credential *and* Origin Basic auth) must remain expressible. Validation is empirical, not predictive.

**Credential storage** — [ADR-0001](../adr/0001-credentials-keystore-wrapped-in-accountmanager.md): Keystore-wrapped ciphertext in `AccountManager` userdata. Consequence: credentials can be replaced, never revealed; and Keystore keys do not survive device-to-device restore, so a restored Account must **detect unreadable credentials and prompt** rather than reporting an auth failure.

**Validation**: at save time, with `PROPFIND Depth: 0`. The save succeeds regardless; the result is reported immediately. `PROPFIND` and not `OPTIONS` — on the real server an unauthenticated `OPTIONS` returned **400**, a misleading signal, while `PROPFIND` gave cleanly distinguishable 207 / 302 / 401 ([#2](https://github.com/t1nk333r/dav-provider-android/issues/2)).

**Header entry**: generic name/value rows, plus a "Cloudflare Access" shortcut seeding the two correctly-named rows. The shortcut exists because a misspelled header name and a rejected token produce **the same 302**, making it the most confusing available error.

**Export**: all Accounts, one file, through the system file picker, **passphrase-encrypted with secrets included**, carrying `formatVersion`.

## 5. Errors ([#11](https://github.com/t1nk333r/dav-provider-android/issues/11))

### Classification — first match wins

1. Body contains `<error xmlns="DAV:">` → the **Origin** answered. Classify by the DAV condition, **regardless of status**.
2. 3xx with `Location` containing `/cdn-cgi/access/login` → proxy rejected the Credentials.
3. `WWW-Authenticate` with a realm → the Origin wants its own Credentials.
4. HTML body on a DAV method → proxy interference.
5. No response → transport class.
6. Otherwise → classify by status.

> **The HTTP status alone never determines severity.** A `403` with a `DAV:` body is informational; a `302` is a hard credential failure. Both were observed on the real server. Any implementation that switches on status first reproduces the opacity this app exists to remove.

### Taxonomy

| # | Class | Discriminator | Summary line | Retry | `SyncResult` |
| --- | --- | --- | --- | --- | --- |
| 1 | Proxy rejected credentials | 3xx → Access login | "Access denied by the proxy — the token is wrong or expired" | no | `numAuthExceptions` |
| 2 | Origin wants credentials | `WWW-Authenticate` | "The server needs a username and password" | no | `numAuthExceptions` |
| 3 | Origin refused (**info**) | `<error xmlns="DAV:">` | per condition, e.g. "this collection doesn't support fast sync — using a slower method" | no | none |
| 4 | Certificate unavailable | KeyChain null/throws | "The selected certificate is no longer available — reselect it" | no | `numAuthExceptions` |
| 5 | Credentials unreadable | Keystore decrypt fails | "Credentials can't be read — this happens after restoring a device. Re-enter them." | no | `numAuthExceptions` |
| 6 | No certificate sent | certificate configured **and** callback never fired **and** nothing answered **and** an `SSLException` in the cause chain | "No certificate was sent" | no | `numAuthExceptions` |
| 7 | Transport failure | no response | "Couldn't reach the server" | **yes** | `numIoExceptions` |
| 8 | Server error | 5xx, 429 | "The server is having trouble" | **yes** | `numIoExceptions` |
| 9 | Not found | 404 | "That path doesn't exist on the server" | no | `numParseExceptions` |
| 10 | Method refused | 405, or 400 on `OPTIONS` | "The server rejected this request type" | no | `numParseExceptions` |
| 11 | Malformed response | a response **arrived** and its body could not be parsed or read to the end | "The server's response couldn't be understood" | no | `numParseExceptions` |
| 12 | Proxy refused / interference | HTML body, no redirect | 403: "The proxy refused this request before it reached the server", and with a certificate on the wire "— a certificate was sent but not accepted"; otherwise "Something between the app and the server changed the response" | no | `numAuthExceptions` |

- **Class 3 is `info`**: it must not mark a Collection failed nor contribute to "Partial".
- **Class 6 is worded as observation, not conclusion.** "No certificate was sent" is checkable; "the server required one" is an inference TLS cannot support.
- **Class 6 is all four conditions at once**, not any of them. A bare connection failure with a certificate configured is **class 7**, retryable: a server that is merely down must not be reported as a certificate problem, least of all as a terminal one that never retries. The `SSLException` is the only evidence that a handshake happened at all — the alias callback can only fail to fire if there was a handshake for it to fire in.
- **Evidence about a response is never read before establishing that there was one.** An EOF while waiting for the status line looks like a parse failure but means nothing arrived, so the "did anything arrive" gate runs first and it classifies as class 7. Reading the cause chain first made a transient disconnect non-retryable.
- **Evidence is reset at each DAV operation boundary**, not per HTTP hop — a redirect must survive within an operation, but an unanswered request must not inherit the previous request's `207`.
- **Retry is delegated to the framework** by setting the right `SyncResult` field. No retry loop inside `onPerformSync` — it would duplicate platform backoff and risk the cancellation rule in §6.

### Surfacing

One-line plain-language summary with a suggested action; a **Details** expander carrying, verbatim: HTTP status, first body line, whether a certificate was offered, request method. Account status is **`OK` / `Partial` / `Failed`** with a per-Collection breakdown — one broken Collection must never mask the others. Notifications fire **only for terminal classes** (1, 2, 4, 5, 6).

**Log**: capped ring buffer of recent attempts, viewable and shareable. **Redaction is absolute** — header *values* and passwords never enter it; header *names* do, because a misspelled name is a real failure mode and is not a secret.

**Diagnose action**: user-initiated only, bounded at four requests (with credentials / without headers / without certificate / unauthenticated), presenting the status matrix. Never automatic — credential-varying retries resemble an attack and risk rate-limiting a service token.

## 6. The sync algorithm ([#12](https://github.com/t1nk333r/dav-provider-android/issues/12))

Per run, per Account, **Collections sequential**:

0. **Upload (step U)** ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)) — for a **writable** Collection only, and before anything is fetched: the pending changes, deletions then creates then updates, each serialised and sent as `DELETE` with `If-Match`, `PUT` with `If-Match`, or `PUT` with `If-None-Match: *` for a create. A row's `DIRTY` is cleared only by an answer that accepted it; a `412` is a conflict, and the server's version wins. A read-only Collection runs the same step in **refuse** mode instead — what it holds is reverted, counted and logged rather than sent. Uploading first is not a detail: the fetch's wholesale row replacement would otherwise discard the edit before it was sent.
1. **Cheap check** — `PROPFIND Depth: 0` for `getctag`. Unchanged → Collection done.
2. **List** — `PROPFIND Depth: 1` for `href` + `getetag`. Diff against stored ETags → adds, updates, deletes.
3. **Fetch** — `addressbook-multiget` / `calendar-multiget`, **batches of 50**.
4. **Write** — per batch: contacts, then groups and memberships. Commit and persist those ETags.
5. **Reconcile** — local pass for memberships whose target never arrived; count and log skips.
6. **Delete** — only if step 2 completed: remove rows absent from the listing.
7. **Finish** — persist the Collection's CTag, and only now.

An **upload-only run** — the framework asking for one because a provider reported a dirtying write — does step 0 for every writable Collection and stops: no listing, no deletion, no state write. It still fetches what a revert left behind, because those rows are waiting for the server's version and no listing is coming to bring it.

`sync-collection` collapses steps 1–2 into one `REPORT` **where supported**. Support is re-probed weekly, on server-version change, or after failure; the first `REPORT` attempt *is* the probe and `<supported-report/>` is the negative answer, so detection is free. **The real server refuses it**, so the polling path above is the one that runs ([#2](https://github.com/t1nk333r/dav-provider-android/issues/2)).

### Invariants

1. **Rows may be written before a Collection completes; its CTag may not.** Partial rows are re-confirmed cheaply; a premature CTag strands missing items forever.
2. **Deletion runs only against a listing that completed** — and a listing the server said it cut short did not complete, however well-formed it was. **Assert this in code.** It is the only invariant here whose violation destroys user data.
3. **Sync state lives with the data** — item ETags on the row, Collection state in the provider's sync-state store. If it lived in a separate database it would survive the provider's account cleanup and leave the app convinced it was current with an empty provider.
4. **A run stores Collection state only for what it actually learned.** The CTag and the sync token are what the *next* run trusts, so neither may be written by a run that received no body for an href its own listing named, or whose listing was truncated. Such a run reports the Collection **incomplete**: not OK, not an error class, no notification — and its stored state left exactly as it was found, so the next run lists again instead of short-circuiting on a state that was never earned. A sync token the server rejects (`valid-sync-token`) is not a failure either: the same run lists in full and says so. **A pending upload is not a reason to withhold it** ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)): that upload is a `DIRTY` row, read from the provider at the start of every run rather than discovered through the CTag, so withholding state for it would re-list the Collection in full on every run for as long as one body is refused — the stall this invariant exists to remove, reintroduced from the write side.

### Framework constraints

- A non-user-initiated sync transferring **≤10 bytes in any 60-second window is cancelled**. Batches of 50 keep traffic flowing; additionally, a sync triggered from Account setup is marked `SYNC_EXTRAS_MANUAL`, exempting the first sync.
- The documented 10-minute per-sync timeout no longer exists in current AOSP; do not rely on it either way.
- A **terminal auth failure (classes 1, 2, 4, 5) aborts the Account's remaining Collections.** Anything else is Collection-specific and must not stop the others.

## 7. Provider writes ([#13](https://github.com/t1nk333r/dav-provider-android/issues/13))

### Contacts identity

| Column | Carries |
| --- | --- |
| `RawContacts.SOURCE_ID` | DAV href / filename; a contact created on the phone has none until its upload is answered |
| `SYNC1` | vCard UID — for a created contact, minted once and stored before the first upload attempt, so a retry reuses the same name |
| `SYNC2` | ETag |
| `SYNC3` | **Collection id** |

Lookup before every insert is **`(account, SYNC3, SOURCE_ID)`**. `SYNC3` is a deliberate addition: one Account spans many Collections, so filenames are not unique across them.

### Account registration — the data-loss hazard

`ContactsProvider2` deletes groups and raw contacts for any `ACCOUNT_TYPE`/`ACCOUNT_NAME` **not registered in `AccountManager`** ([#6](https://github.com/t1nk333r/dav-provider-android/issues/6)). Three rules:

1. The account exists in `AccountManager` **before any row is written**.
2. **Assert at sync start**; abort if absent.
3. **Re-check before each batch commit** — a user can remove the Account mid-sync, most likely during a long first sync.

### Fidelity

- **Store the original vCard verbatim** in a custom MIME row: the read path is lossless at rest, so an upload sends back more than it was given instead of destroying the properties this app does not map.
- **Count and log unmapped properties** per sync.
- **Names**: `N` → `StructuredName` components, `FN` → `DISPLAY_NAME`; let Android derive `DISPLAY_NAME` only when `FN` is absent or trivially redundant.
- **Photos**: thumbnail **and** full-size via `DisplayPhoto`, downscaling oversized images.
  - **Security**: a `PHOTO;VALUE=uri` pointing off-origin must **never** be fetched with the authenticated client — that would send Account Credentials to a host named by the data. Same-origin only; otherwise skip and log.
  - **An upload keeps the source's `PHOTO` unless the photo itself changed**, and what decides that is a **digest of the photo's bytes** held in the photo row's `SYNC2` ([#31](https://github.com/t1nk333r/davkeep/issues/31)). It must not be a version counter: AOSP's `data_updated` trigger increments `DATA_VERSION` on every update of a `Data` row, including the write that records the baseline, so a version baseline is false as soon as it is stored — measured on a device as `data_version=1, data_sync2=0` on a freshly synced row, and observed to replace a server's 8932-character `PHOTO` with a 6660-character re-encode on an edit that only touched the name. The provider re-encodes what it is given, so the comparison is between successive re-encodes, never against the bytes the server sent.
- `CALLER_IS_SYNCADAPTER` on **every** write. Uniformity is what lets the one write that clears `DIRTY` — after the server has accepted that row's upload — not re-dirty the row it just cleared.
- **A Collection is written only when the user has made it writable** ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)). The flag is per Collection and defaults **off**, so an upgrade writes nothing until the switch is turned on. Neither `supportsUploading` nor `<EditSchema>` can be told about one Collection, which is why the engine enforces it. Read-only means **refuse**, not ignore: step U reverts what such a Collection holds, counts it as refused and logs why, and the same run fetches those resources by href so the revert is visible at once — the server changed nothing, so no listing would have named them.
- **`DIRTY` is cleared only by an answer the run accounts for**: the server's `2xx` to that row's own upload; a body the server already holds, acknowledged without a request; a `412` or a refusal, which reverts the row and is reported; or a conflict the restore resolves, which is reported as one. No sync clears it as a backstop — a row whose edit was never answered is a row whose edit has not been sent.
- **The answer is applied to the row that was read, or not at all** ([#30](https://github.com/t1nk333r/davkeep/issues/30)). A row can move between the moment step U reads it and the moment the server's answer is written back, and an answer applied to the newer row clears an edit nobody sent. Every write that claims a row is current carries, in its selection, the one fact its provider keeps about movement, and everything depending on that claim commits in the same transaction:
  - **Contacts**: `RawContacts.VERSION`, which the provider moves on every insert, update or delete of a contact's data rows whoever makes it. The clear after a 2xx, the revert after a 412 or a refusal, and the fetch's replacement of an existing row all match the version step U read; the rows re-derived from the sent body and the photo baseline are in that same batch under an expected count, so a moved row rolls the whole claim back. It is a counter of the rows a vCard is made of, and only those: a raw-contact-level write — `STARRED`, `CUSTOM_RINGTONE`, `SEND_TO_VOICEMAIL`, `PINNED` — sets `DIRTY` without moving it. Such a write reaches no property of the resource, so the body it would send is the one the server already holds, and **a body that says nothing new is acknowledged instead of uploaded**: no request goes out, `DIRTY` is cleared under the same version the answer to a real upload is guarded by, and the change is counted neither uploaded nor pending. A row that moved while step U was deciding fails that guard, keeps its flag and is held out of this run's fetch — that edit is newer than the decision and the next run sends it. The measure of "nothing new" is the resource, not the bytes: the source and the patched card are written by the one writer and compared before this app stamps its own `PRODID` and `REV`, which are the only difference such an upload ever carried. Calendars have the same shape — an event's access level, its colour, anything no column of the resource holds marks the row dirty without moving a property, and the serialiser says when it rewrote nothing — so both providers answer it the same way.
  - **Calendar**: there is no counter, so the flag carries one bit more. Every non-deleted row of a resource is set to `DIRTY=2` before its body is read; every editor path in `CalendarProvider2` writes the literal `1`, so a row that is no longer `2` was touched while the request was in flight. Only rows still at `2` are cleared, and a resource with any row left dirty or deleted stays pending. The revert after a 412 goes further and is **all-or-nothing across the resource**: the batch asserts, before writing anything, that no row of the resource has left `2`, and the provider applies a batch in one transaction, so a resource with any moved row keeps every value it had — its ETag above all. Reverting row by row cleared the master while a sibling kept its edit, and the master's revert drops the ETag: the resource stayed pending, holding the body the server had just refused, with no version left to be conditional about. A refusal sends nothing and therefore arms nothing, so a refused revert guards on the row still being dirty instead — without that, a read-only Collection would revert nothing at all; it stays row by row, because no `PUT` can follow it.
  - **A resource's only tombstone is its master's.** `CalendarProvider2` hard-deletes an event row that carries no `_SYNC_ID` rather than marking it `DELETED=1`, exceptions never carry one — the provider explicitly does not clone `_SYNC_ID` into an exception, and this app writes it on the master alone — and deleting a master hard-deletes the exceptions hanging off it. The stock app's "delete this occurrence" is not a deletion at all but an exception inserted or updated with `STATUS_CANCELED`, which is an ordinary dirty row. So no override can arrive at step U as a tombstone, and the guards that say `DELETED=0` exclude nothing that can exist. An override row an editor deletes outright therefore leaves **no trace at all**: nothing dirty, no tombstone, and the master untouched. So the master keeps the count of override components its stored text gave rows to (`Events.SYNC_DATA4`, written by the fetch and by the answer to an upload alike), and fewer live override rows than that count queues the resource — with every component no row claims dropped from the text that is sent, and no `EXDATE` invented for it, because locally the master's own occurrence has come back.
  - Identity and the ETag are written **before** that transaction and unguarded: the server does hold that body under that name, and the next `If-Match` must say so whether or not the phone's row moved.
  - **A `PUT` for a resource the server already has always carries `If-Match`.** A row whose ETag is null cannot say which version it is replacing, and sending it unconditionally is client-wins with extra steps; so the version is asked for — one `PROPFIND Depth: 0` for `getetag`. What the answer says decides whether the `PUT` goes at all. Every path that stores a text on a row stores the ETag the server named for it, so a row that holds a text and no ETag, on a server that names one, holds a text the server's current version was never read from: a revert left it there after a `412` said the server had moved, and the restore that was to replace it has not landed. Patching the edit onto that text and sending it under the ETag just asked for would put the stale base back over the version the `412` was about, with nothing to refuse it — so it is not sent, and the resource goes to the restore's conflicted half below: the server's copy replaces the rows and the run reports a conflict. Only a server that names no ETag at all leaves the `PUT` to go, under `If-Match: *`, which still says the resource must exist: such a row's text can be nothing but the version the server holds, and holding the edit back would strand it on a server whose ETag this phone can never store.
  - A guard that matches nothing writes nothing, and the run reports the change as pending, holds its resource out of the same run's fetch, and meets the same answer next run against the row as it is then. The cost is that a row edited mid-upload is uploaded twice; the second `PUT` carries the ETag the first earned, so nothing is clobbered. A held resource does **not** hold back the Collection's CTag or sync token: the row is found again by `pendingChanges` whatever the state says, and withholding it would cost a full listing on every run for as long as a server keeps refusing one body.
  - **A revert fetches the resource it gave back, by href, before the listing** — and the set is read from the rows at every run, not carried from the step U that made it: a master that is named, clean and carries no ETag is a row holding text nobody kept. A revert leaves exactly that shape, and only the server's copy belongs there; a `sync-collection` delta names what changed since the stored token, so a conflict whose server-side change an earlier run already consumed, and a refusal on a Collection the server never touched, would otherwise leave the row looking clean while holding an edit the run deliberately gave up. Reading it from the rows is what makes a fetch that fails once a fetch the next run makes again. The ETag stored with it is the one that multiget's own response named, because there is no listing here to read one from. An explicit `404` for an href is the server deciding by name that it no longer has the resource, and the resource's clean rows are removed; an href the multiget did not answer at all is counted missing, so the run does not report as done, and is asked for again next run.
  - **A named row with no stored text is fetched even while it holds an edit, and the fetch resolves it as a conflict** ([#35](https://github.com/t1nk333r/davkeep/issues/35)). A create the server answers `412` is reverted under the name it was `PUT` to, and that name arrives with no copy of the server's text behind it; a restore that fails — the server unreachable, or answering without that href — leaves it so. Edit the event then, and the row is dirty: it drops out of the clean-rows-only set above, and the serializer holds it, because a keyed resource with no stored source has nothing for a patch to start from. Every run would count the edit pending and none would ever fetch anything. So the restore asks for those hrefs too — the ones the queue means to `PUT` and the rows have no text for — and writes the server's copy over the rows, clears their flags and **reports a conflict**, which is what this design does with every conflict. Keeping the edit and giving it the fetched text as a base is what the rows cannot support: they were never written from the server's text, so a body patched out of them would carry back every column another client had changed in the meantime, under an ETag this phone obtained by fetching, with no `412` to refuse it and nothing reported. A resource held back for its size is not asked for; a clean text-less row still takes the whole restore above, which gives nothing up.
  - **A `404` asks one question of the whole resource: does any row of it hold a change no run has sent?** No — its rows are the server's, and the server no longer has them, so they go. Yes — nothing is deleted and the resource gives the name and the ETag back instead: an `If-Match` against a resource the server does not have can only fail, a text-less row cannot be serialised to try, and every restore would ask again and be answered `404` again. Its overrides stay and are relinked by `ORIGINAL_ID`, because the name they claimed is gone and a master sent without them would be a recurrence with the user's exceptions silently dropped. Every row of it is marked `DIRTY` in the same write, which is what keeps the same run's deletion sweep from taking it: an unnamed clean row claims no href, so no listing can name it, and a master deleted without a `_SYNC_ID` takes its exceptions with it. Marked, the rows are an event this phone has and the server does not, and step U sends them as a create under the UID the name was made from. A master that is a tombstone keeps everything, name included, because the `DELETE` it owes is addressed by it.
  - **A `404` to a conditional `PUT` is read as a `412`.** RFC 9110 makes `If-Match` fail against a resource with no current representation, and Radicale and sabre answer `412`; an origin that answers `404` instead is saying the same thing by another number. Left as an error, the row was counted pending and held on every run with no way out; as a refusal it is reverted, and the restore's own `404` for the href is the answer that removes its rows or makes them a create again. A create's `404` stays an error: it is about the Collection.
  - **The question a `404` asks is asked in the transaction that acts on the answer.** The calendar's delete of a resource's clean rows and the assertion that none of them is dirty or a tombstone are one batch, so an edit saved between the two is not deleted through the sync-adapter URI unreported; the delete carries `DIRTY=0 AND DELETED=0` in its own selection as well.
  - **A server copy the phone cannot hold resolves the restore the only other way.** A body the restore fetched and could not write — text that does not parse, a master with no usable start — is not an answer to leave the rows waiting for: every run would ask for the same body again. Rows a revert left are removed if none holds an unsent change, decided in the same transaction as the delete; rows holding an edit that could never be sent are removed with it and the run reports the conflict. Either way the phone shows what a listing would have given such a resource, which is no rows, and the server still holds it: a body that becomes readable is fetched by the next listing that names it. The listing itself still skips such a body and keeps the rows it has — a resource the provider cannot hold must not withhold the Collection's state, which would list it in full on every run.

### Account removal

Removal asks what happens to the rows, and **keeps them by default**. There is no way to keep a row
without keeping the account it belongs to — the provider reaps the rows of an unregistered account,
as above — so an account that "goes" takes its rows with it whether or not this app deletes any.

- **Keep** (the default) — the account stays registered, keeps its rows, and has its configuration
  taken away: base URL, Credentials, certificate, Collection selection, schedule, sync state, log.
  It then reads as **disconnected**, and **Configure** fills it in again. Because the account never
  moved, the rows did not either: the next sync finds them by ETag and writes nothing.
- **Delete** — the account goes, and the provider reaps its rows with it.

Explicit cleanup in the authenticator's removal path stays what it was — provider rows (on delete),
sync state, stored Credentials, ring-buffer log, export preferences — with one correction: the
**Keystore key is per app, not per account**, and every account's Credentials are wrapped with it,
so removal never deletes it. Only the account's own ciphertext and record go, with its userdata.

### Calendars ([#16](https://github.com/t1nk333r/dav-provider-android/issues/16))

| Meaning | Column |
| --- | --- |
| DAV resource **path** (the href's absolute path, percent-encoding preserved) | `Events._SYNC_ID` — master row only; overrides are NULL, and a resource created on the phone has none until its upload is answered |
| ETag | `Events.SYNC_DATA1` — master row only, beside the resource text the read path stored in `SYNC_DATA2`, which an upload patches ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)); `SYNC_DATA3` marks a text withheld for size |
| iCalendar `UID` | `Events.UID_2445` |

**The canonical key everywhere in `ProviderMapper` is the href's absolute path** — `/user/collection/item.ics`, scheme and authority stripped exactly once during listing, nothing else derived from it. `localItems`, `upsert`, `etags` and `deleteMissing` all speak that same string, so the listing's keys and the stored keys are identical by construction. That identity is what keeps `deleteMissing` from mass-deleting.

This supersedes the deployed convention of storing only the last path segment. `_SYNC_ID` is compared opaquely, and `doesEventExistForSyncId` counts by it **with no calendar filter**, so `/cal/a/x.ics` and `/cal/b/x.ics` would collide as bare segments. Storing the path also keeps one identity per row, rather than forcing a second column to hold what `localItems` must return.

`_SYNC_ID` is unique **per calendar only**, and there is no unique index — de-duplication is entirely the adapter's job. It must be stable across all components of one resource, which is why the path is correct and the UID is not.

**Storage-syntax invariants — the provider silently scrubs violations rather than erroring:**

- A **recurring master carries `DURATION` and must not carry `DTEND`**; a **non-recurring row and every override carries `DTEND` and must not carry `DURATION`**. A recurring event written with `DTEND` loses it and expands to **zero-length instances**, accepted without error.
- `RRULE` holds a **bare** value; `RDATE`/`EXDATE` hold `[TZID;]yyyyMMddTHHmmss[Z],…`, not the iCalendar property text.
- All-day rows: `ALL_DAY=1`, `EVENT_TIMEZONE="UTC"`, times truncated to UTC midnight.
- `EVENT_TIMEZONE` **must** be a zone ID Android's tzdata knows — an unrecognised ID silently falls back to GMT. Resolve a `VTIMEZONE` `TZID` to a system `ZoneId` **before** writing.

Not carried by v1 **as columns**: `RECURRENCE-ID;RANGE=THISANDFUTURE`, `EXRULE`, and everything without a first-class column (`CATEGORIES`, `URL`, `COLOR`, `SEQUENCE`, `X-*`, `CREATED`/`DTSTAMP`/`LAST-MODIFIED`). They are not lost by an upload — they live in the stored text an upload patches ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)) — only invisible to anything that reads the rows alone.

**What the calendar's own row declares** ([#28](https://github.com/t1nk333r/dav-provider-android/issues/28)): `CALENDAR_ACCESS_LEVEL` is `CAL_ACCESS_OWNER` for a writable Collection and `CAL_ACCESS_READ` otherwise, refreshed at the start of every run. This is the calendar side of the per-Collection rule: it is how the stock app is told that this calendar is not to be edited, and why it greys out the editor rather than letting the edit be refused later. `ALLOWED_REMINDERS` and `ALLOWED_AVAILABILITY` list what an upload can carry, so the app offers only that.

## 8. Discovery, selection, scheduling ([#14](https://github.com/t1nk333r/dav-provider-android/issues/14))

**Discovery**, falling back progressively rather than failing at the first step: `.well-known/carddav` + `.well-known/caldav` → `current-user-principal` → home-set → enumerate; on failure, root-as-principal, then root-as-Collection; then **surface every attempt with its outcome**. A pasted Collection URL skips discovery.

Discovery **reuses the §5 classifier**. A `3xx` to a web UI is not a Collection — behaviour the real server exhibits.

**Selection**: `displayname`, falling back to the URL's last segment, with type and colour from the same `PROPFIND`. No item counts. A UUID name is shown as-is, never disguised. A Collection that disappears is marked **unavailable, not deleted**. Re-enumeration is manual plus daily; **new Collections default to unselected**. A Collection the user named by **pasting its URL is pinned**: it lives outside the home sets a walk enumerates, so no enumeration may retire it — its absence from a listing is the expected result rather than news about the server, and only the sync's own answer for that URL says otherwise.

**Scheduling**: per-Account interval via the sync-adapter APIs. **Unmetered-only is enforced in-app** — check connectivity, do nothing, set `SyncResult.delayUntil`; there is no public API for it. A **manual sync bypasses every constraint**. A deferred sync shows "waiting for Wi-Fi" with a **"sync anyway"** action. The battery-optimisation exemption is requested **only after observing missed syncs**, with the evidence shown, once, permanently dismissible.

## 9. Acceptance criteria

From `prompt.md`, restated as checks:

1. An Account configured with **only a client certificate** syncs the server's contacts and events into the system providers.
2. An Account configured with **only two custom headers** (a proxy service token) syncs the same, with no VPN and no client certificate.
3. Both mechanisms together work.
4. Toggling any other app's network state has no effect on sync — no VPN is involved anywhere.
5. A deliberately wrong configuration (bad certificate, wrong header, wrong URL) produces an error naming **the HTTP status and whether a certificate was offered** — never a generic "no services found".
6. A second sync **updates rather than duplicates**: run twice, row count unchanged.
7. A sync interrupted mid-Collection **converges on the next run**, with no duplicates and no stranded items.
8. A recurring event with an exception instance renders correctly in the stock calendar app — not as zero-length instances.

## 10. Non-goals for the implementer

Do not implement: keep-both or client-wins conflict handling — the server's version wins — attendee and organiser write-back, group vCards, moving an item between Collections, `current-user-privilege-set` discovery, tasks, scheduling/free-busy, sharing or ACL, a WorkManager hybrid, an adaptive multiget batch size, or item counts at setup. Each was considered and rejected; the reasoning is on the linked tickets, and write-back itself, which v1 now implements, is [#28](https://github.com/t1nk333r/dav-provider-android/issues/28).
